## 0. 三十秒项目介绍

> "这是一个基于 C++17/Drogon 的高可靠交易与对账系统,覆盖下单、支付回调、可靠消息、日终对账全链路。核心是解决三个问题:钱不能算错、消息不能丢、重复请求不能重复扣款。四个深度点:防超卖用条件更新+行锁,100 并发抢 50 库存零超卖;幂等用唯一索引抢占+响应快照,重放逐字节一致;可靠消息用本地消息表同事务写入+publisher confirm+手动 ACK+死信,broker 宕机 5 轮退避后恢复送达;对账按渠道交易号逐笔核对,差异自动分型人工核销。"

**为什么选这个题**:交易/对账是银行、运营商、电网信息化部门的核心业务形态,面试官有专业语境,能问出深度;而"可靠性"是这类系统最被看重的品质。

**为什么用 C++**:核心交易/清算系统的存量代码大量是 C/C++,延迟与资源确定性有真实需求;同时这是展示现代 C++ 工程能力(RAII、智能指针、模板)的载体。Drogon 是 C++ 生态里少有的高性能异步 Web 框架。

## 1. 防超卖(亮点①)

**问题**:100 个并发请求同时买最后 1 件库存,如何保证不超卖、且不牺牲太多并发?

**方案**:把「判定」与「扣减」合并成一条原子 SQL,靠 InnoDB 行锁与受影响行数判定:

```sql
UPDATE t_product SET stock = stock - ?, version = version + 1
 WHERE id = ? AND stock >= ? AND status = 1;
```

```cpp
if (dao->deductStock(tx, pid, qty) == 0) throw BizException(kStockNotEnough);
```

**权衡(必被追问)**:

- **为什么不用「先 SELECT 再 UPDATE」?** TOCTOU 竞态:两个线程都读到 stock=1,都通过判断,都执行扣减 → 库存 -1。压测必现。
- **为什么不用 `SELECT ... FOR UPDATE`?** 能防超卖,但间隙锁会锁住不存在的行(REPEATABLE READ 下),锁冲突面放大、死锁概率上升。条件 UPDATE 只锁真实被改的行,更简单更快。
- **为什么不用乐观锁(version/CAS)?** 乐观锁要求「先读旧值再算新值写回」,高并发下重试成本随冲突率指数上升,吞吐反而差;且它适合余额这类必须读旧值的场景。库存扣减是"相对量"运算(减 N),条件 UPDATE 天然原子,不需要读旧值 —— 用对场景比用对工具更重要。version 字段我保留做辅助审计,不参与判定。
- **affectedRows == 0 的歧义**:库存不足或商品下架都会返回 0。判定依据永远是 affectedRows;提示语区分靠扣减失败后补查(但补查结果不是判定依据)。
- **库存何时归还**:下单即扣(进入支付流程前),超时关单(OrderTimeoutTask)归还。扣减与订单创建同事务。

**验证数据**:`scripts/stress_stock.sh`,100 并发抢 50 件库存 → 成功恰 50、拒绝恰 50、库存恰 0、负库存 0。

## 2. 接口幂等(亮点②)

**问题**:渠道回调必然重发、客户端必然重试。同一个请求重复到达,如何保证只生效一次?

**方案**:三层防线。

1. **t_idempotent 抢占**:先 INSERT(request_id 唯一索引,status=0 处理中)→ 业务 → UPDATE 写回响应快照(status=1)。唯一键冲突即「他人已处理/处理中」。
2. **语义边界**:与业务**同事务** —— 业务失败回滚,幂等键一并释放(不留"永远处理中"的僵尸记录);冲突且 status=0 → 返回 10003 让客户端稍后重试(绝不返回虚假成功);status=1 → 返回快照。
3. **业务唯一索引兜底**:`t_order.uk_request_id`、`t_payment.uk_channel_trade`、`t_account_flow.uk_request_biz` —— 即使幂等表被绕过,业务层仍然拒绝重复写入。

**权衡(必被追问)**:

- **幂等和防重有什么区别?** 防重只保证"同一请求同一时刻"不重复;幂等保证"同一请求任意时刻任意次数"结果一致,包括失败后的重试、跨进程的重放。幂等是防重的超集,且必须持久化(键存数据库,不存进程内存)。
- **快照返回的坑**:快照必须与首次在线响应**逐字节一致**,否则客户端 diff 两笔响应会误判。我实测踩过:jsoncpp 的 `toStyledString()` 是美化格式,与 drogon 的紧凑序列化不一致 —— 快照统一用与 drogon 相同的 StreamWriterBuilder 配置(commentStyle=None, indentation="")。另一个注意点:快照是**成功结果**,失败请求不缓存 —— 失败重试必须重走流程。
- **已知取舍**:先到者执行失败后,后到者重试会重走整个流程(等价新请求)。下单/回调可接受(业务层唯一索引兜底);V1.5 升级路径:幂等表独立事务 + 租约超时(处理中超时视为死占可抢占)。
- **request_id 从哪来**:写接口强制 X-Request-Id(过滤器统一校验,长度 16-64 的 UUID/32 位十六进制),贯穿日志/幂等键/消息头/流水,全链路可追踪。

**验证数据**:同一 X-Request-Id 重放 N 次只生效一次(库中订单数不变),响应 `diff` 逐字节一致;渠道重复回调(同 channelTradeNo)不重复入账。

## 3. 可靠消息(亮点③)

**问题**:业务数据已提交,但下游通知(商户回调)不能丢 —— 如何保证「订单支付成功」这件事最终一定送达?

**方案**:本地消息表(事务消息模式的简化版),四步:

1. **同事务写入**:业务写操作(订单翻转/出账/流水)与 t_local_message 记录在**同一个 MySQL 事务**内落库 —— 业务成功消息必在,业务回滚消息必无。
2. **独立投递**:MessageRelayTask 每 5s 扫描 `status=0 AND next_retry_time<=NOW()`,publish 后**以 publisher confirm 为准**判定送达(不是 publish 不抛异常就算成功),confirm 成功才置 status=2。
3. **手动 ACK 消费**:消费者 autoAck=false,处理成功才 basic_ack;失败 nack(requeue=false)转死信队列。
4. **幂等兜底**:至少一次投递必然产生重复消息 —— 消费端以 uk_message_id 去重,重复直接 ACK 跳过。

**权衡(必被追问)**:

- **为什么不在事务里直接发 MQ?** 双写不一致:MQ 收到但事务回滚 → 下游拿到不存在的订单(脏消息);事务提交但 MQ 失败 → 消息丢失。外部系统的成败无法与本地事务原子提交,二者之间必然存在不一致窗口。本地消息表把「发消息」变成「写数据库」,把跨系统一致性降级为系统内一致性。
- **为什么不在事务提交后立即发 MQ?** 提交与发送之间宕机,消息永久丢失。投递必须与业务解耦、由独立任务驱动。
- **本地消息表 vs 事务消息(RocketMQ) vs 2PC?** 2PC 是同步强一致,阻塞与协调器单点成本高,交易链路一般不用;事务消息把半消息存到 broker,比本地消息表少一张表和一次轮询,但强绑定 MQ 厂商;本地消息表最简单、可迁移性最好,代价是至少一次投递 —— 必须配消费幂等。三者本质都是"先持久化意图,再异步执行"。
- **至少一次 vs 恰好一次**:通用共识是端到端恰好一次不现实(分布式事务不可靠),工程实践是"至少一次投递 + 消费端幂等",对外效果等价恰好一次。
- **投递任务防重入**:单实例原子标志;多实例需 `SELECT ... FOR UPDATE SKIP LOCKED` 或 Redis 分布式锁(防多副本重复投递)。

**验证数据**(本次实测):broker 宕机时消息 retry_count 递增至 5(退避 5s/10s/20s/40s/80s),broker 恢复后下一轮送达、status 翻 2 —— **消息没丢,只是迟到**;重复投递消费端 skip;商户不可达时消费者内重试 2 次(1s/2s)后 nack 转死信,`trade.dead.queue` 兜底(人工介入)。

## 4. 日终对账(亮点④)

**问题**:渠道账单与本地流水不一致时,如何定位到具体哪一笔、差多少、谁多谁少?

**方案**:

1. **口径统一**:本地侧按 `callback_time`(渠道时间戳)归集 —— 不按本地创建时间。23:59:58 发起的支付、渠道记到次日 00:00:01,以渠道账单为准是通行做法。
2. **逐笔核对**:以 channelTradeNo 为键,分类纯函数(`classifyReconcileDiffs`,单测覆盖):本地有渠道无 → 本地多单(1);渠道有本地无 → 渠道多单(2);两侧都有金额不等 → 金额不一致(3)。差额 = 本地 − 渠道,符号即方向。
3. **批次幂等**:`uk_date_channel` 防同日重复跑批;定时任务每分钟检查"账单就绪 && 当日未对账"才触发。
4. **人工核销闭环**:差异查询 → 核销/忽略(带 handle_status=0 条件更新,重复核销返回 70003)→ 备注留痕。

**权衡(必被追问)**:

- **"本地多单"的常见真因不是资损,而是渠道账单延迟** —— 所以对账要支持历史日期重跑(V1.5 规划,uk_date_channel 已为覆盖更新预留语义)。
- **长款/短款**:本地多单≈渠道少收(长款),渠道多单≈渠道多收(短款)……严格说要看具体场景;核销时人工备注区分,这正是"人工介入"的价值。
- **对账前置条件**:当日订单必须已终态化(超时单已关单),否则"处理中"订单会被误判。

**验证数据**:注入三类差异各 1 笔(gen_bill.sh 的 --missing/--extra/--tamper)→ 跑批恰好 3 笔差异、类型各一、金额差分毫不差(+199.00 / −199.00 / +5998.99)→ 核销生效、重复核销 70003、同日重跑 70002。

## 5. 架构决策问答

**Q:为什么 Service 层用同步事务 + 线程池,而不是 Drogon 的异步回调链?**
A:这是核对源码后的决策,不是风格偏好。三个事实:① `execSqlSync` 的 Blocking 模式在 `f.get()` 上阻塞等结果(SqlBinder.cc),而 MySQL 结果依赖事件循环投递 —— 在循环线程调用同步接口必然死锁;② fast 客户端(`is_fast=true`,1.9 默认)把 DbClient 绑到 IO 循环,其 `newTransaction()` 直接 assert(0);③ Drogon 的 `~Transaction()` 是**隐式提交**(TransactionImpl.cc:35-86),没有显式 commit 方法 —— 事务 RAII 的确定性保证在回调链里根本写不出来。所以:同步事务统一跑在固定线程池(Controller 只提交任务,响应 queueInLoop 切回循环线程),配 TransactionGuard(显式 `execSqlSync("commit")` 提交、失败抛异常、析构兜底回滚)。这套组合同时满足"提交失败必须抛异常"与"任何异常路径必然回滚"两条硬约束。代价:每个在途请求占一个池线程 —— 演示规模无感,生产按 DB 连接数配比。

**Q:金额为什么全程用整数分?**
A:`0.1+0.2 != 0.3`,double 累加十万笔差额可能到几十元 —— 资损。DB 存 DECIMAL(18,2),应用层 int64_t 分运算,边界转换收敛在 MoneyUtil:写库转"元字符串"参数化绑定(不经 double),读库 `CAST(col*100 AS SIGNED)` 直接取分。展示层才转字符串元。

**Q:时区怎么处理?**
A:应用侧显式 UTC+8(中国无夏令时,固定偏移精确),不依赖进程 TZ —— 实测容器里 TZ 环境变量根本不可靠。MySQL 侧 `--default-time-zone=+8:00`,两侧 NOW() 口径对齐。expire_time 应用侧算好随 INSERT 写入(不回读)。

**Q:订单状态机怎么防并发重复流转?**
A:状态流转带原状态条件 `WHERE order_no=? AND status=0`,靠 affectedRows 判定 —— 与防超卖同一思路,单向禁止回退。

## 6. 排障实录(面试素材:「你踩过什么坑?」)

每个都是真实发生、有源码/证据链支撑的:

1. **"服务崩溃,只因为数据库没启动"** —— Drogon 1.9.11 在中间件不可达时连接失败处置路径段错误(两次复现:Redis/MySQL 各一次)。排查:崩溃紧跟连接失败日志 → 拉 v1.9.11 源码定位 MysqlConnection.cc:125-133(fd<0 → closeCallback 后崩)。处置:升级 1.9.13、启动前确认中间件健康、部署侧 restart 兜底。教训:框架也会崩,别默认"框架没问题"。
2. **"验签全拒,secret_len=0"** —— 配置放对了文件、字段也对,但 `getCustomConfig()` 只返回 `custom_config` 段(v1.9.13 源码直接 `jsonConfig_["custom_config"]`),顶层自定义段被静默忽略。教训:框架的"自定义配置"有专属入口,别按直觉放。
3. **"连接卡死 15 秒后超时,全程无报错"** —— TCP 建连成功、MySQL 握手永不完成。真相:host.docker.internal 经 Docker Desktop 转发到宿主回环,撞上了 Windows 原生 MySQL(占用 3306)。教训:网络路径上每一跳都要验证(netstat 看监听者)。
4. **"端口映射在配置文件里,却怎么都不生效"** —— 宿主端口被原生服务占用时,Docker Desktop 容器照常启动、映射**静默失效**(ps 无宿主机映射)。教训:冲突不总是报错,验证要用 `docker compose ps` 看映射是否真的在。
5. **"幂等快照重放不一致"** —— 快照用 `toStyledString()`(美化)存,在线响应是紧凑格式 —— 内容一致、字节不一致,diff 客户端会误判。教训:快照要按"字节"定义一致性。
6. **"编译期 API 猜谜"** —— 连续踩了三个 Drogon 1.9 的 API 形态变化:无 `TransactionPtr` 别名、`execSqlSync` 返回 Result 值而非指针、`Field` 用 `as<T>()` 而非 jsoncpp 风格。教训:接新库先核对头文件,凭旧经验写=批量返工。

## 7. 高频追问速查

- 幂等键过期怎么办?→ 定时清理,V1.5 租约。
